# Nzoia Flood CAT Model — web app

Next.js front-end for the Lower Nzoia (Budalangi) riverine flood catastrophe model. It runs the
full Hazard → Vulnerability → Exposure → Financial → EP-curve chain **in the browser**, using the
artefacts exported by `../notebooks/nzoia_flood_cat_model.ipynb`.

## Run

```bash
npm install
cp .env.example .env.local   # optional: add GEMINI_API_KEY or OPENAI_API_KEY to enable the LLM features
npm run dev                  # http://localhost:3000
```

Node 22.5 or newer is required because the app uses Node's built-in SQLite driver.

Other scripts:

| Script | Purpose |
| --- | --- |
| `npm run build && npm start` | Production build |
| `npm run validate` | Re-runs the TypeScript engine and checks it against the notebook's `results.json` |
| `npm run lint` | ESLint |

## Where the data comes from

`public/data/*.json` and `public/hazard/*.png` are **generated by the notebook** (section 6). To
change the model (training data, vulnerability parameters, gazetteer), edit
`../notebooks/_build_notebook.py`, then:

```bash
cd ../notebooks
python _build_notebook.py
python -m jupyter nbconvert --to notebook --execute --inplace nzoia_flood_cat_model.ipynb
cd ../web && npm run validate
```

| File | Content |
| --- | --- |
| `portfolio.json` | 500 synthetic buildings, TIV corrected to documented values, with sampled depths |
| `hazard.json` | Sparse JRC depth cells for the six return periods (10–500 yr) |
| `vulnerability.json` | Trained ML damage grid (mean + 5/25/50/75/95 % quantiles) and adapted JRC curves |
| `results.json` | Notebook results, used for parity checks and the methodology page |
| `gazetteer.json` | Approximate town coordinates for accumulation and geocoding |
| `explain.json` | Global SHAP values for the deployed vulnerability model (optional — written by `../notebooks/explain_shap.py`) |

To refresh the global SHAP export after retraining: `python ../notebooks/explain_shap.py` (needs `shap`).

## Portfolio storage

The portfolio has two separate layers:

- `public/data/portfolio.json` is the immutable 500-building starter portfolio exported by the
  notebook. Refreshing model artefacts can replace this file without touching accepted offers.
- `data/nzoia.sqlite` stores only buildings accepted from the Underwriting desk. It is created
  automatically. Copy this file with the project to transfer the working portfolio.

The Portfolio page can remove one accepted batch or **Reset to original 500**, which clears only
the SQLite table. On the first run after this change, any buildings in the old
`localStorage["nzoia.ingested.v1"]` store are migrated into SQLite and the browser copy is removed.
Set `NZOIA_DB_PATH` to use a database file elsewhere.

## Pages

- **Underwriting desk** (`/`) — the AI workflow, in five steps:
  1. paste an offer or upload a `.docx`;
  2. the LLM extracts buildings, with an evidence quote and a provenance tag on every value;
  3. per-building damage ratios and losses at every return period, plus the financial waterfall
     (ground-up → deductible → limit → gross → quota share → Cat XL → net) and the EP curve;
  4. SHAP and LIME explanations of each building's damage ratio, plus global SHAP;
  5. impact on the book, accept/decline, and an AI briefing.
- **Portfolio** (`/portfolio`) — the whole book: total exposure, losses at key return periods,
  waterfall, EP curve (deterministic, Monte Carlo and the JRC baseline), class and area
  breakdown, flood map.
- **Model & assumptions** (`/methodology`) — financial terms glossary, how the AI is explained,
  vulnerability curves and ML validation, data sources, assumption register and limitations.

SHAP and LIME for individual buildings are computed in the browser (`src/lib/explain.ts`) against
the same damage function the engine uses. Exact Shapley values over 4 features, so they add up
exactly; LIME is a kernel-weighted linear surrogate with a reported fidelity R².

All model settings (vulnerability model, hazard sampling, duration, terms, correlation, simulated
years) live in the **Model settings** drawer; defaults reproduce the notebook.

## LLM

`/api/ingest` and `/api/briefing` call either Google Gemini (`GEMINI_API_KEY`, `GEMINI_MODEL`; a free
Google AI Studio key works) or any OpenAI-compatible endpoint (`OPENAI_API_KEY`, `OPENAI_MODEL`,
`OPENAI_BASE_URL`). If both keys are set, Gemini is used. LLM output is always sanitised (class
whitelist, counts clamped, coordinates checked against the hazard grid, places matched to the
gazetteer) before it reaches the engine. Without a key, both routes degrade to deterministic
fallbacks and the header pill shows "LLM: offline fallback".

### Building photos (optional)

The desk accepts up to 4 photos per offer. They are resized to ≤1024 px and re-encoded in the browser
(which strips EXIF/GPS), sent with the text to the same vision-capable model, and never stored. Photos
may only fill three fields the document leaves unstated — construction class, raised-floor height and
condition (`good`/`fair`/`poor` → build quality 0.85/0.5/0.15) — and are tagged "from photo" on the desk.
When a photo contradicts the document, the document's value is kept and the conflict is flagged on the
desk and in the briefing. The keyword parser ignores photos and says so. The "Proposal + site photo"
example uses a CC BY-SA 4.0 Wikimedia Commons image (see `public/samples/ATTRIBUTION.txt`).
